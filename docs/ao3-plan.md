# AO3 functions: plan

Plan for the AO3 work that is still open: the loose ends of Phase 11 (chapter HTML export and tag suggestions, built 2026-11-13) and all of Phase 12 (proofreading mode and AO3 sync, not started). Written 2026-11-21 and agreed in scope with the maintainer (Phase 12 plus the Phase 11 gaps). Update the checkboxes at the end of every unit of work. Deviations from PLAN.md go in `docs/decisions.md`.

## Where things stand (checked in the repo)

- `libertum-export` (model only): `chapters()` splits at the heading levels chosen in Settings; `ao3_fragment()` and `chapter_html()` write a fragment limited to `AO3_WHITELIST`; `tags.rs` ranks the writer's own vocabulary against a chapter with BM25 and `tags_to_text()` writes the ticked tags as one comma-separated line.
- The app shows the chapter list (Export > AO3 Chapter), a chapter window with the HTML and Copy HTML, the suggested tags (nothing ticked to begin with) and Copy tags, and a vocabulary window (Settings > AO3 tags).
- `libertum-library` keeps version history (`snapshot`, `versions`, `restore`) and detects a file changed on disk (`DiskStamp`). **There is no text diff engine and no HTML importer.** The formats that open are DOCX, ODT, RTF, Markdown and the native `.lbtd`.
- No AO3 network code exists. The app's only network uses are the update check and the opt-in MCP HTTP client.

## What AO3 offers (from AO3's own pages, searched 2026-11-21; some pages are old, so re-check each point before building on it)

- **Posting:** the Work Text field is an HTML editor by default, with a Rich Text toggle. Pasting HTML into the Rich Text editor produces a work full of raw tags. Drafts are deleted one month after creation and there is no autosave while editing, so writing offline and pasting in is the safer workflow. Sources: [Posting and Editing FAQ](https://archiveofourown.org/faq/posting-and-editing?language_id=en), [Formatting content on AO3 with HTML FAQ](https://archiveofourown.org/faq/formatting-content-on-ao3-with-html?language_id=en).
- **Downloads:** every work can be downloaded as AZW3, EPUB, MOBI, PDF or HTML. Source: [Downloading Fanworks FAQ](https://archiveofourown.org/faq/downloading-fanworks?language_id=en).
- **Automated access:** there is no official API. The [Terms of Service FAQ](https://archiveofourown.org/tos_faq) says scraping for spam, commercial promotion or other policy-violating purposes is forbidden, that other scraping is generally allowed, and that AO3 may add `robots.txt` limits, ask a scraper to stop, or ban a program. [Scraping commercially is prohibited](https://archiveofourown.org/tos). AO3's [admin guidance](https://archiveofourown.org/admin_posts/25888) asks scrapers to pause between requests and to put "bot" in the user agent. **This is a summary of dated pages, not legal advice; read the current terms before any network code.**

## Open decisions (Phase 12 cannot start without them)

1. **How a draft gets from AO3 into Libertum.** Options, safest first: (a) the writer saves their own work from AO3 (HTML or EPUB download) and opens that file, so Libertum never talks to AO3; (b) the writer pastes a chapter's HTML; (c) the writer gives a URL for one of their own works and Libertum fetches that single page on request; (d) a browser extension or logged-in session. The recommendation is (a) and (b) only. (c) and (d) bring terms-of-service, rate-limit and credential questions, and (d) would have to store a session.
2. **Whether any network call to AO3 is acceptable at all.** If yes, it is user-initiated, one page per click, with a delay, a user agent that says "bot", no credentials stored, and no use of anything behind a login.
3. **What "proofreading mode" means for this writer:** a read-only review pass with suggested edits to accept or reject, or a side-by-side comparison against what was last posted. The plan below builds the comparison first because the other needs a new kind of model content (tracked changes and comments are refused by the DOCX and ODT readers today).

## Phase 11 gaps (small, each independent)

- [ ] **11a. Paste check against AO3's own editor.** The one acceptance item PLAN marks as not done on this machine: paste a fragment from a fixture book into AO3's HTML editor and check emphasis, lists, headings, quotation marks and block quotes. Needs a human with an AO3 account (no automation, no login by us). Output: a short checklist in `docs/` and one fixture per problem found.
- [~] **11b. Verify `AO3_WHITELIST` against AO3's HTML FAQ. Partly done 2026-11-21.** The live FAQ page could not be read: AO3 answered the fetch with HTTP 429 (rate limited), and under this plan's own rules the fetch was not retried. A search (which does not touch AO3's servers) found that AO3's own pages disagree: the FAQ's "full list of allowed tags" as extracted omits `blockquote`, `h1` to `h6` and `img` (probably an extraction fault, since bold and italic also failed to extract), while the [Posting a Work tutorial](https://archiveofourown.org/faq/tutorial-posting-a-work-on-ao3?language_id=en) and the [HTML help page](https://archiveofourown.org/help/html-help.html) list them. Every tag in our whitelist (`p`, `h1`-`h6`, `em`, `strong`, `u`, `s`, `sup`, `sub`, `blockquote`, `ul`, `ol`, `li`, `table`, `tbody`, `tr`, `td`, `br`, `hr`, `img`) is in the tutorial's list, and the export writes no attributes, so nothing we emit is outside either list. **Still to do:** read the live FAQ once the rate limit has cleared (one request, later, by hand or with a pause) and confirm the list, then add a fixture for any difference. Do not repeat the request soon.
- [x] **11c. Tags one field at a time. Done 2026-11-21, then withdrawn the same day by request.** Per-category Copy buttons were built and then removed: the review list keeps its tick-boxes (the writer selects the tags they want) and one **Copy tags** button copies the ticked ones as a single comma-separated line, leaving out the rating and warnings. The catch: AO3 has separate fields for fandoms, relationships, characters and additional tags, so the one line has to be split by hand or pasted into one field.
- [x] **11d. Rating and warnings from AO3's fixed lists. Done 2026-11-21.** AO3 takes the rating and the warnings as choices on its posting form (a selection and tick boxes), not as typed text, so the plan's "let the writer pick" became: `AO3_RATINGS` and `AO3_WARNINGS` in `libertum-export` (names from AO3's own pages, found by search; **re-check them against the live form**, in particular "Underage Sex" against the older "Underage"); the vocabulary window's name field becomes a **picker** when the category is Rating or Warning, and a free-typed name is refused for those two; in the chapter window those two categories show "Choose on AO3" instead of a Copy button, and the combined **Copy tags** line leaves them out (pasted into a tag field they would only make stray tags). Existing vocabulary entries are kept. Checked in screenshots of both themes. **Not done, and worth knowing:** AO3's form also has a **Category** choice (Gen, F/F, F/M, M/M, Multi, Other) that Libertum has no place for; adding it would be a new vocabulary category.
- [x] **11e. Chapter title. Done 2026-11-21 (title only, as requested; no summary or notes buttons).** The chapter window has a **Copy title** button that copies the chapter's heading text as plain text, for AO3's chapter title field. The whole-document chapter (a document with no matching heading) has no real title, so it gets no button. Checked in screenshots of both themes.
- [x] **11f. Tags suggested from the chapter's own text. Done 2026-11-21 (added by request).** `libertum_export::auto_suggestions` (new `autotags.rs`, model only) proposes **characters** (capitalised names that recur, with a title such as "Captain" dropped when the name mostly stands alone), **relationships** (pairs of those characters who share paragraphs, written `A/B` only where romantic cue words appear in their shared paragraphs and `A & B` otherwise) and **additional tags** (the words the chapter leans on, after names, function words and a list of common narrative words are set aside). It needs no vocabulary, makes no network call, never suggests the fandom (not detectable from the text), a rating or a warning, and every suggestion says what earned it ("mentions x8", "paragraphs together x5, romantic cue words in x2"). A tag the vocabulary already has is not offered twice. The chapter window has a checkbox for it (Settings `auto_suggest_tags`, on by default) and a one-line caution. **Known limits, on purpose:** a name that is also an ordinary word (Hope, Mark) is taken for the word; a name seen only opening sentences needs four mentions; keywords have no corpus to be compared with, so they are the noisiest; the pairing order follows who is mentioned more, not AO3's convention; it assumes English prose. Speed: about 38 ms for 40,000 words in a release build (about 0.3 s for a 300,000-word whole-document chapter), run only when the chapter window opens.

## Phase 12, in stages (each stage is useful on its own and works offline)

**Stage A: bring an AO3 download in (needs decision 1, options a and b).**
- [x] A1. **HTML importer** (done 2026-11-22, crate `libertum-html` on `html5ever`; see decisions.md; AO3 fixtures are hand-made and still need checking against a real download) for AO3's HTML download and for pasted chapter HTML: paragraphs, emphasis, headings, block quotes, lists, horizontal rules, line breaks, tables, images by reference. New crate `libertum-html` (model only, no UI), with a fixture per construct and a round trip through `libertum-export`'s own fragment writer as the test. **Dependency risk:** `html5ever` is MIT or Apache-2.0, but `scraper` pulls in Servo's selector crates, which are MPL-2.0 (rule 4 then forbids them): verify before choosing, and otherwise write a small tolerant tokenizer for the whitelisted tags only.
- [x] A2. **Open with... and Import chapter** (done 2026-11-22: Open reads `.html`/`.epub`, AO3 downloads and EPUBs open as new unsaved documents; Insert > Chapter from File… / Chapter from Copied HTML) in the app, as a new document or into the open one (a stitch-style choice), never overwriting the open file.
- [x] A3. EPUB import (done 2026-11-22, `libertum_html::import_epub`) is a later extension: the EPUB is a zip of XHTML chapters, so it can reuse A1.

**Stage B: compare with the last posted text (no network).**
- [x] B1. **Diff engine** (done 2026-11-22, crate `libertum-diff` on `similar`) in a new `libertum-diff` or inside `libertum-export` (model only). Licences checked with `cargo info` on 2026-11-21 (transitive dependencies not yet checked): `similar` 3.2.1, `dissimilar` 1.0.11 and `imara-diff` 0.2.0 are all Apache-2.0, which rule 4 allows. Compare at paragraph level first, then words inside a changed paragraph. Never on the keystroke path: run on request, off the UI thread, with a cap on size (a book is hundreds of pages).
- [x] B2. **"Last posted" copy.** (done 2026-11-22, `libertum_library::posted`) Store the text of each chapter as it was when the writer last marked it posted, in the document's history folder beside the existing versions (`libertum-library`), with a clear label and date. Nothing is uploaded; this is a local copy only.
- [x] B3. **Comparison window:** (done 2026-11-22 as an inline mode, View > Compare with Posted, by the user's choice) pick a chapter, see the changes against the last posted copy (added, removed, changed), jump to each, accept or ignore. Colours as theme tokens for both themes, strings in `strings.rs`, keyboard reachable (see `docs/accessibility.md`).
- [x] B4. **Mark as posted** button (done 2026-11-22, in the compare bar): records the current chapter text as the new "last posted" copy. Explicit, never automatic.

**Stage C: proofreading mode (needs decision 3).**
- [ ] C1. If suggested edits are wanted: design the model (a suggestion is a range, replacement text, author and status) with an exact inverse for every operation and an entry in the model proptest, then the editor commands and the UI. This is the largest item and the one most likely to change the native format (`docs/format-libertum-native.md`), so it comes with a decision-log entry and fixtures for save and reopen.
- [ ] C2. Decide what DOCX and ODT do with suggestions (comments and tracked changes are refused today). Probably flatten on save with a warning, as other native-only features do.

**Stage D: talking to AO3 (only if decision 2 is yes).**
- [x] D0. **Spike first** (2026-11-22: decided that Libertum makes no AO3 requests at all; see decisions.md) (PLAN §9, Phase 12):** write down exactly which AO3 pages would be fetched, how often, and what happens on a refusal, then get approval before any code.
- [ ] D1. If approved: a single-page fetch of a public work the writer owns, one per click, with a pause between requests, a user agent that says "bot", no credentials or cookies stored, honouring `robots.txt`, and a failure that never loses a local edit (PLAN §9). Fetching goes through the existing opt-in network path rather than a new one.
- [ ] D2. **Withdrawn 2026-11-22: Libertum stays offline** (a browser-assisted version was built and removed by request; the chapter window's copy buttons and Mark as Posted remain). Original item: Draft versus published: show both states and require an explicit "update draft" or "update published chapter" step. **Posting to AO3 from Libertum is out of scope**: it needs a login, and the plan never silently publishes (PLAN §9).

## Rules that apply to all of it

- Nothing here touches the keystroke path. Imports, diffs and fetches run on explicit actions, off the UI thread, with a size cap.
- Every format feature needs a round-trip fixture under `tests/fixtures/` and every new behaviour needs tests (rule 9).
- New dependencies: permissive licences only, logged in `docs/decisions.md` when added (rule 4). Ask before anything GPL, LGPL or MPL.
- User-facing text in `strings.rs`, colours as tokens in both themes, icons from Lucide (rules 3 and 5). Screenshots in both themes for every UI change (`LIBERTUM_SCREENSHOT` works on GNOME Wayland).
- The app must work fully offline, and no password or session cookie is ever stored.

## Suggested order and rough size (rough estimates, not measured)

1. Gaps 11b and 11c first: small and useful at once (about a day each).
2. 11a whenever someone can sit with an AO3 account (about an hour, once).
3. Stage A (the HTML importer is the bulk: a few days with fixtures), then Stage B (a few days). These two answer most of "proofreading against the posted version" with no network at all.
4. Stage C only after decision 3; Stage D only after decision 2.
